# ADR-033 — BREAKEVEN Trade Excluded from OANDA Fills Summary

**Date:** 2026-04-30
**Status:** Accepted
**Repo:** theonlykk/candlelab
**Author:** Khalid Khan (Lead Engineer)
**Reviewer:** Gemini (Staff Architect)

---

## Context

`api_strategy_oanda_fills` bucketed closed trades as wins (`oanda_pl > 0`)
or losses (`oanda_pl < 0`). BREAKEVEN trades (`oanda_pl == 0.0`) fell
through both conditions and were silently excluded from `total` and
`closed`. For Calm Crimson Crane: 15 actual closed trades, 1 BREAKEVEN
→ `closed=14`, `win_pct=14.3%` instead of correct `closed=15`,
`win_pct=13.3%`.

## Decision

Option A — Add BREAKEVEN bucket with epsilon guard.

**Rejected:**
- Option B (use Postgres `result` for classification): unmatched fills
  have no `pg_match`. Coupling broker summary to DB match-rate is
  an unacceptable failure mode.

## Changes

- `app.py`: `breakevens = 0` initialised alongside `wins`/`losses`.
- Bucketing uses `EPSILON = 1e-4` to absorb micro-dust from OANDA
  pip fractional conversions. Anything below 0.01 cent is BREAKEVEN.
- `total = wins + losses + breakevens` — BREAKEVEN is a real trade.
- `summary` now includes `breakevens` field.
- `win_pct = wins / total` — breakevens in denominator, not numerator.
  A BREAKEVEN tied up margin and incurred opportunity cost.

## Consequences

- `closed` is now a true count of all settled trades.
- `win_pct` accurately reflects "% of all executed trades that
  profited" — no artificial inflation from excluding breakevens.
- Frontend receives new `breakevens` field — no breaking change.
- Future UI can surface breakeven count if needed.

## Negative Space

- Does NOT change `/api/strategy/true-pnl`.
- Does NOT change win/loss classification logic — only adds the
  third bucket.
- Does NOT touch the frontend JS.
